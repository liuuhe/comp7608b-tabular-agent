# v17：报告修正后的复查上下文

## 触发问题与最终实现

[v16浏览器运行](DEV_BROWSER_V16_ZH.md)中，同一句缺失值说明在修正前后逐字相同，
逐条审查却由fail变pass。生成修正稿的调用有旧反馈，但复查只看到当前报告：
verification_feedback仅在重试verify时提供，报告修正后没有相应历史。

当前控制器在一次完成但未通过的审查后，保留被审查的实际可见文本及判断。仅在复用
相同计算的报告／审查修正中，将先前失败的具体语句、理由、修正要求和当前原文匹配
位置交给复查，保存为report_revision.json。匹配不依赖旧索引，支持语句移动和重复；
改写后的不匹配不等于错误已修好。新计划或新代码清空历史，格式失败不会覆盖上一份
真正完成的审查。额外的请求覆盖、计划等判断继续由当前审查评估，不作为旧事实复制。

提示要求：未改动不能被称为已修正；若旧批评本身错误，可依据实际代码／结果重新判断，
但应说明理由。没有把旧模型判断硬编码成永久失败，也没有自动改写报告或补全判断。

还修复一处反馈作用域问题：成功生成有效报告后清空已消费的生成反馈。后续审查格式
重试只携带该次格式错误，历史具体语句的批评通过独立上下文保留，避免混入旧泛化批评。
模型JSON schema、重复判断的拒绝规则、调用路由及token／工具／修正上限均未放宽。

三项控制器回归在初始代码下失败；反馈泄漏另由一项失败断言复现。最终413项测试通过，
包含真实Docker，10.04秒；Ruff通过。测试覆盖中间报告／审查格式失败后的历史保留、
重算／重规划清理、重排／重复／改写、实际可见文本匹配和旧误判可重新考虑的边界。
