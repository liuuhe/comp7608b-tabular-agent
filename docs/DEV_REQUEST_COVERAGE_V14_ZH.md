# 请求覆盖审查：v14开发验证

## 修复的问题

v13的D6报告给出了三个正确的总体缺失计数，却漏掉题目要求的类别差异分析。原审查逐条
接受了报告并给出整体通过。逐条检查已写出的陈述，不能代替检查用户要求但未写出的内容。

新增必填 `request_coverage` 判断，要求对照完整请求说明计划、结果及报告覆盖了哪些要求，
指出遗漏，并给出修正位置。缺分析时修正计划；已有结果但没有回答时只改报告。该判断
属于原有full条件的审查调用，不新增工具／模型调用，不改变12工具、3次修正和token上限。
缺失、重复或不确定判断阻止整体通过；覆盖失败也不能被模型的整体pass覆盖。

## 完整D6流程

另以同一候选配置完成一次 `pilot-request-coverage-v14` 的D6/full运行，验证实际修正路径。
运行ID为 `20261107-221516-cd380f87`，共570.6秒、48,120个模型报告token、4次工具、
3次修正，最终状态 **failed**。

1. 初始计划仍只有三个总体缺失计数；第一次代码执行成功，生成三个表和三个图。
2. 两次报告修正依次处理无支持的百分比和裸引用格式，复用第一次计算。
3. 新审查明确判请求覆盖失败，要求增加类别差异，触发第三次修正并实际重新规划。
4. 新计划按education、race、workclass计数非缺失income，但替换掉原来的缺失分析。
   这些count操作只衡量组样本数，不构成收入分布比较。该计划没有执行。
5. 最后代码生成输出达到6,144 token上限，无法解析为完整代码；控制器按既定修正上限
   停止，保留失败及全部用量。较早的候选仍可查看，但其请求覆盖失败没有被改成通过。

本轮证明新审查的反馈实际到达规划节点，不能证明补做分析成功或整题质量提升。代码
截断、计划替换已有正确内容，以及模型把组计数命名为收入分布，仍是可检查的失败边界。
数据和原始v12／v13结果保持不变，不能把本轮并入原完整三条件比较。

在关闭本次测试服务后，对这个真实失败批次执行了 `--resume`：未新增运行或模型调用，
stdout仍只有一条原始记录，stderr记录保留D6/full/r0。批次登记的completed表示选定网格
已经结束，逐次任务的summary仍是failed，两者含义不同。

Streamlit AppTest另打开了该真实失败结果，验证失败提示、截断错误、三张表与下载控件，

证据保存在 `../evaluation/private/request-coverage-v14-ui.json`。
