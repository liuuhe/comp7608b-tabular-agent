# v26代码生成与请求范围检查

2026-11-15。本轮针对[18次开发基线](DEV_LOCAL_COMPARISON_20261115_ZH.md)暴露的问题，
优先修复本地执行稳定性。它是定向开发验证，不是新的完整三条件比较或正式实验。

## 实现

- 真实模型的代码响应改为`lines`数组，每项是一行Python，保留缩进与合法字符串转义。
  适配器只用换行符连接，仍保存原始响应、逐行响应和规范`Program.code`；不代写计算。
  旧保存代码和CLI／worker接口继续使用`code`。
- 生成节点保存`analysis.py`后用`ast.parse`检查语法，无效代码保留并反馈行列、错误和原文。
  一次生成条件直接失败，恢复条件仍按既有预算重生成；未进入Docker的代码不计容器调用。
  语法解析不会执行代码，也不证明代码计算正确。真实执行继续只在原Docker隔离环境中进行。
- 新开发候选[local-stable-v26.json](../config/local-stable-v26.json)显式关闭代码thinking，
  保留审查thinking、原模型、上下文、输出／累计token和工具／修正上限。旧候选与所有
  历史结果保持原样。应用默认原本就关闭全局／代码thinking，设置不变。
- 规划提示强调覆盖各个请求主题、需求与解释变量的关联及完整时间组；报告提示强调
  指标／类别／日期角色；审查提示把原题要求放在前面，不追加合并计数曲线或逐行叙述要求。
  这些提示不保证语义正确，实际仍有下述失败。
- 浏览器真实流程进一步暴露“行数冒充求和”漏检，因而增加窄范围的确定性请求检查。
  明确的英文整体sum／total子句需有具名数值列的非分组sum分析；有分组措辞时不强制
  整体求和。含“number of”的表达只有同时要求valid count才检查，以缩小歧义范围。
  列名来自实际数据概况、数值转换和声明派生字段，不接触外部评估答案，也不写死152。
  通过只说明操作／分组存在，筛选和报告含义仍需其他检查；不声称覆盖任意中英文措辞。
